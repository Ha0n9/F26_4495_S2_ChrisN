# JSON contract: PowerShell module to dashboard

Two files. The module produces the first one. The second is hand written content that ships with the project and is never generated by a scan.

| File | Produced by | Contains |
|---|---|---|
| `scan-result.json` | PowerShell module, one per scan | What was found, as raw technical data |
| `finding-dictionary.json` | Written by hand, versioned in the repo | What each check means in plain language, and what to do about it |

The dashboard loads both and joins them on `checkId`.

## Rules

1. The module never writes explanation or remediation text. If a string in `scan-result.json` would read like advice, it belongs in the dictionary instead.
2. The dictionary never contains scan data. It describes check types, not specific accounts.
3. `checkId` is the join key and is permanent. Once a check ID ships, it does not get renamed. Retire it and add a new one instead.
4. A finding is one issue of one type. Multiple affected objects go in `affectedObjects`, not in multiple findings.
5. `severity` in the scan result wins over `defaultSeverity` in the dictionary. The dictionary value is only a fallback when the module does not set one.
6. If the dashboard receives a `checkId` that is missing from the dictionary, it still renders the finding using `checkId` as the title. It does not crash and it does not hide the finding.

## Fields the dashboard depends on

From `scan.*`: domain name, timestamps, module version, and the three coverage lists described below. Every scan result is validated against this contract before it is rendered, whichever route it arrived by, because a result that is merely shaped like a scan crashes the renderer on its first missing field.

## Coverage: three outcomes, not two

A check ends in one of three states, and the envelope records each separately because collapsing any pair of them tells the reader something untrue.

| List | Meaning |
|---|---|
| `checksCompleted` | The check ran to the end without error. |
| `checksFailed` | The check threw. Its entries carry `checkId` and `errorMessage`. |
| `checksPartial` | The check ran to the end without error but did not examine all of its ground. Its entries carry `checkId` and `reason`. |

`checksPartial` is the one that is easy to get wrong. A check that abandons a branch of a group hierarchy at its depth limit has not failed: it returned real findings that must still be shown. Nor has it covered the domain: accounts below that branch were never looked at. Recording it only in `checksCompleted` presented unexamined ground as clean, which is the failure this project argues against everywhere else. Recording it in `checksFailed` instead would discard findings the check did produce.

So a truncated check appears in **both** `checksCompleted` and `checksPartial`. The first says it ran; the second says how far it got. The dashboard shows it as `Partial` in the coverage table, raises a banner, and marks the security score as a partial view even when every requested check completed.

`checksPartial` was added after the first scans were written, so a reader must treat its absence as an empty list rather than as invalid. Every committed baseline predates it.

From each finding: `checkId`, `severity`, `affectedObjectCount`, `affectedObjects`, `evidence`.

`affectedObjects[].attributes` is an open object. The dictionary entry's `keyAttributes` lists which of them to show as table columns. Everything else appears only in the expanded technical detail.

## Severity

Fixed enum, ordered: `Critical`, `High`, `Medium`, `Low`, `Info`. No other values. The dashboard maps each to a tag colour and sorts by this order.

## Version handling

`schemaVersion` is present in both files. The dashboard checks the major version and refuses to render a file from a newer major version rather than showing wrong data.

## Suggested rendering

- Summary row at the top: domain, scan time, count per severity, count of failed checks.
- One table of findings, sorted by severity. Columns: severity, title (from dictionary), affected object count, category.
- Each row expands to show: `whyItMatters`, `whatToDo` as a list, a table of `affectedObjects` using `keyAttributes` as columns, and the raw `evidence` object.
- No nested containers inside the expanded row. Tables and description lists sit directly in it.

## Open items to decide before coding

- Whether `findingId` stays deterministic (`checkId:domain:index`) or becomes a GUID. Deterministic is easier to diff between two scans later.
- Whether the health score is computed in the module or in the dashboard. Computing it in the dashboard keeps the module free of presentation logic, which fits the architecture described in the proposal.
